## 主要问题列表

### [必须修复]

#### 1. MutationApplier 的 errors 切片重置方式存在隐患

**位置：** [`internal/parser/applier.go:18`](internal/parser/applier.go:18)

```go
a.errors = a.errors[:0]
```

**问题：** 这种方式虽然能清空切片，但如果 `a.errors` 为 nil（例如直接通过 struct literal 创建 MutationApplier），会 panic。虽然 Parser 中通过 `NewParserWith` 保证了初始化，但 MutationApplier 本身没有防御性处理。

**建议：**
```go
func (a *MutationApplier) Apply(schema *model.Schema, mutations []SchemaMutation) error {
    a.errors = make([]error, 0)  // 改为重新分配，更安全
    // 或者添加 nil 检查
    // if a.errors == nil { a.errors = make([]error, 0) }
    // else { a.errors = a.errors[:0] }
    ...
}
```

---

#### 2. CreateEnumTypeMutation 和 CreateIndexHandler 的 Apply 方法未实现

**位置：** [`internal/parser/mutation.go:108`](internal/parser/mutation.go:108) 和 [`internal/parser/index_handler.go`](internal/parser/index_handler.go)

**问题：** 这两个类型已注册到 DefaultRegistry，但 Apply 方法返回 "not implemented" 错误。如果 SQL 中包含 CREATE TYPE 或 CREATE INDEX，解析会失败并返回错误。

**建议：**
- 如果 MVP 范围不包含这些类型，建议在文档中明确说明
- 或者在 Handler 中返回更友好的错误信息，说明"暂不支持，请关注后续版本"

### [建议修改]

#### 3. HandlerRegistry 使用 reflect.Type 作为 key 可能有性能开销

**位置：** [`internal/parser/registry.go:16-32`](internal/parser/registry.go:16)

**问题：** `reflect.TypeOf(node)` 在每次 Dispatch 时都会调用，有一定性能开销。对于 parser 这种可能被频繁调用的场景，可以考虑优化。

**建议：** 如果后续出现性能瓶颈，可以考虑：
- 使用节点类型的标识符（如字符串）作为 key
- 或者在解析前预分配一个类型到 handler 的映射缓存

目前阶段这个问题不紧急，可以作为后续优化点。

---

#### 4. AlterTableHandler 中未处理的 AlterTableCmd 子类型会静默跳过

**位置：** [`internal/parser/alter_table_handler.go:40-42`](internal/parser/alter_table_handler.go:40)

```go
default:
```

**问题：** 除了 AT_AddColumn 之外的子类型（如 DROP COLUMN、RENAME COLUMN 等）会被静默跳过，用户可能不知道这些语句被忽略了。

```go
default:

```
