## 逐文件审查

### 1. [建议修改] `cmd/migra/diff_runner.go` — format 回退逻辑

```go
if format == "" {
    format = viper.GetString("diff.format")
}
if format == "" {
    format = "sql"
}
```

**问题：** 这个回退链暴露了一个设计上的时序问题——cobra flag 注册时默认值为空字符串，导致无法区分"用户显式传了空字符串"和"用户没传"。虽然当前修复是务实的，但根本原因在于 flag 注册时应该直接设置默认值 `"sql"`。

**建议：** 在 `init()` 中将 flag 默认值改为 `"sql"`：

```go
diffCmd.Flags().String("format", "sql", "output format (sql, json, ...")
```

这样回退到 viper 的逻辑仍然保留（允许配置文件覆盖），但 cobra 层就有了合理的默认值，回退链可以简化。当前写法虽然能工作，但属于 workaround，后续维护者可能会困惑为什么需要两层回退。

### 2. [建议修改] `cmd/migra/push_runner.go` — 破坏性操作过滤的重复遍历

```go
if !cfg.UnsafeDrop {
    destructiveCount := 0
    for _, op := range ops {        // 第一次遍历
        if op.IsDestructive() {
            destructiveCount++
        }
    }
    if destructiveCount > 0 {
        fmt.Fprintf(os.Stderr, "Warning: %d destructive operation(s) detected!\n", destructiveCount)
        for _, op := range ops {    // 第二次遍历
            if op.IsDestructive() {
                fmt.Fprintf(os.Stderr, "  - %s: %s (destructive)\n", op.Kind(), op.ObjectKey())
            }
        }
        ...
    }
}
```

**问题：** 对 `ops` 进行了两次完整遍历。虽然在实际场景中 ops 数量通常不多，但从代码质量角度可以合并为一次遍历，同时收集破坏性操作列表。

**建议：**

```go
if !cfg.UnsafeDrop {
    var destructiveOps []diff.Operation
    for _, op := range ops {
        if op.IsDestructive() {
            destructiveOps = append(destructiveOps, op)
        }
    }
    if len(destructiveOps) > 0 {
        fmt.Fprintf(os.Stderr, "Warning: %d destructive operation(s) detected!\n", len(destructiveOps))
        for _, op := range destructiveOps {
            fmt.Fprintf(os.Stderr, "  - %s: %s (destructive)\n", op.Kind(), op.ObjectKey())
        }
        fmt.Fprintf(os.Stderr, "Use --unsafe-drop to include destructive DROP operations\n\n")
    }
}
```

### 3. [建议修改] `cmd/migra/push_runner.go` — `ComputeDiff` 参数顺序

```go
ops, _, err := app.ComputeDiff(targetSchema, sourceSchema, appCfg)
```

以及验证阶段：

```go
remainOps, _, err := app.ComputeDiff(newTargetSchema, sourceSchema, app.Config{...})
```

**问题：** 注意 `ComputeDiff` 的签名是 `ComputeDiff(source, target, cfg)`，但这里传入的是 `targetSchema` 作为第一个参数（source）、`sourceSchema` 作为第二个参数（target）。这意味着 diff 方向是"从 target 到 source"——即计算"需要把 target 变成 source 需要哪些操作"。这是正确的业务逻辑，但参数命名容易让人困惑。

**建议：** 这不是 bug，但建议在调用处加注释说明方向：

```go
// ComputeDiff(source, target): what ops to apply to target to match source
ops, _, err := app.ComputeDiff(targetSchema, sourceSchema, appCfg)
```

或者考虑给 `ComputeDiff` 加一个更语义化的 wrapper，比如 `ComputeDiffToApply(target, desired, cfg)`。

### 4. [仅供参考] `internal/normalize/normalize.go` — 正则表达式编译时机

```go
var charVaryingWithLenRe = regexp.MustCompile(`(?i)^character varying\((\d+)\)$`)
var typeCastRe = regexp.MustCompile(`::[\w\s]+$`)
var nestedTypeCastRe = regexp.MustCompile(`'([^']*)'::[\w\s]+`)
```

**说明：** 使用包级变量编译正则表达式是 Go 的惯用做法，避免了每次函数调用时的重复编译。这是好的做法。不过要注意 `regexp.MustCompile` 在编译失败时会 panic，建议在注释中说明这些正则的预期格式，或者添加单元测试覆盖边界情况。

### 5. [建议修改] `internal/normalize/normalize.go` — `nestedTypeCastRe` 的 `ReplaceAllStringFunc` 用法

```go
expr = nestedTypeCastRe.ReplaceAllStringFunc(expr, func(m string) string {
    sub := nestedTypeCastRe.FindStringSubmatch(m)
    if len(sub) > 1 {
        return "'" + sub[1] + "'"
    }
    return m
})
```

**问题：** `ReplaceAllStringFunc` 的回调函数接收到的 `m` 已经是匹配到的字符串，在回调内部再次调用 `FindStringSubmatch(m)` 是多余的。可以直接用 `ReplaceAllString` 配合替换模板：

```go
expr = nestedTypeCastRe.ReplaceAllString(expr, "'$1'")
```

这样更简洁，性能也更好（避免了在回调中重复匹配）。

### 6. [仅供参考] `internal/normalize/normalize.go` — `typeCastRe` 正则的边界情况

```go
var typeCastRe = regexp.MustCompile(`::[\w\s]+$`)
```

**说明：** 考虑 `nextval('seq'::regclass)` 这个测试用例——`nestedTypeCastRe` 先处理 `'seq'::regclass` → `'seq'`，然后 `typeCastRe` 处理剩下的部分。两个正则的执行顺序很关键，建议添加注释说明各自的职责和执行顺序，避免后续维护者调整顺序时引入 bug。

### 7. [仅供参考] `internal/introspect/tables.go` — `character_maximum_length` 处理

```go
if charMaxLen.Valid {
    dataType = fmt.Sprintf("%s(%d)", dataType, charMaxLen.Int64)
}
```

**说明：** 这个改动让 introspect 返回的类型名带上长度信息（如 `character varying(50)`），然后由 normalize 层统一转换为 `varchar(50)`。这是一个好的设计——数据获取层和规范化层职责分离。`character_maximum_length` 为 NULL 的情况（如 `text` 类型）通过 `charMaxLen.Valid` 正确处理了。

### 8. [仅供参考] `cmd/migra/push.go` — dry-run 默认值变更

