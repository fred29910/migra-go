# migra-go 全方位深度技术评审与可执行优化报告

- 评审日期：2026-05-05
- 评审范围：`cmd/`、`internal/` 全链路
- 证据来源：静态代码审计 + `go test ./...` + `go vet ./...` + `gocyclo` + `go build -gcflags='-m=2'`

## 总体结论（先给结论）

1. 并发原语层面：当前代码几乎不使用 `mutex/channel/goroutine`，没有直接锁竞争与 channel 泄漏风险；但 `Parser` / `Differ` 为有状态对象，复用到并发场景会有 data race 风险。
2. 性能层面：主要瓶颈不在锁，而在“高频小对象分配 + 非确定性迭代 + 重复遍历”。
3. 工程化层面：分层基本清晰（`cmd -> app -> domain packages`），但命令层仍承载了 source-adapter 逻辑，扩展 DB/文件源时会放大耦合。
4. 复杂度层面：核心热点函数复杂度偏高（`diffTables=13`、`addDependencies=13`、`Render=13`、`ComputeDiff=12`）。

## 一、极致性能分析（Performance & Resource Efficiency）

### 问题 1：约束/索引 diff 使用 map 随机迭代，输出顺序不稳定并放大后续排序成本

**【问题定位】**
- `internal/diff/diff_tables.go:70-79` `diffTableConstraints`
- `internal/diff/diff_tables.go:118-129` `diffTableIndexes`

**【缺陷分析】**
当前直接 `range map` 生成操作，顺序不确定。高并发 CI 下会出现同输入不同输出，导致缓存失效、回归基线抖动、无意义 diff。后续 `plan.TopoSort` 无法完全修复该随机性。

**【优化方案】**
统一采用“收集 key -> 排序 -> 生成操作”的确定性路径，并预分配 key 切片容量。

**【代码对比】**
```go
// Before:
for name, index := range target.Indexes {
    if _, exists := source.Indexes[name]; !exists {
        c.addOp(NewCreateIndexOp(schema, index))
    }
}

// After:
addIdxNames := make([]string, 0, len(target.Indexes))
for name := range target.Indexes {
    if _, exists := source.Indexes[name]; !exists {
        addIdxNames = append(addIdxNames, name)
    }
}
sort.Strings(addIdxNames)
for _, name := range addIdxNames {
    c.addOp(NewCreateIndexOp(schema, target.Indexes[name]))
}
```

**【预期收益】**
- 输出 100% 可重现（Deterministic）
- 减少 CI 抖动与“伪变更”
- 为后续 benchmark 建立稳定基线

### 问题 2：`ComputeDiff` 对 destructive op 重复遍历 + `allOps` 未预分配

**【问题定位】**
- `internal/app/diff_service.go:92-104`
- `internal/app/diff_service.go:120-131`

**【缺陷分析】**
`operations` 被扫描两次：第一次统计数量，第二次收集 warning。`allOps` 采用零容量起步追加，存在多次扩容。

**【优化方案】**
单次扫描完成计数与明细收集；`allOps` 按 `len(operations)` 预分配容量。

**【代码对比】**
```go
// Before:
var allOps []diff.Operation
for _, op := range operations { ... } // 第一次
for _, op := range operations { ... } // 第二次

// After:
destructive := make([]diff.Operation, 0, len(operations)/4+1)
for _, op := range operations {
    if op.IsDestructive() {
        destructive = append(destructive, op)
    }
}
allOps := make([]diff.Operation, 0, len(operations))
```

**【预期收益】**
- 减少一次 O(n) 扫描
- 降低 `append` 扩容次数（大 schema 下明显）

### 问题 3：`normalize` 中默认值归一化制造额外堆分配

**【问题定位】**
- `internal/normalize/normalize.go:59-62` `canonicalizeColumnInPlace`
- 逃逸证据：`internal/normalize/normalize.go:60:3 moved to heap: normalized`

**【缺陷分析】**
当前把局部变量 `normalized` 取地址赋给 `col.DefaultExpr`，每个默认值触发一次新分配；在列数大时形成可观 GC 压力。

**【优化方案】**
直接原地改写 `*col.DefaultExpr`，避免临时变量逃逸。

**【代码对比】**
```go
// Before:
normalized := normalizeDefaultExpr(*col.DefaultExpr)
col.DefaultExpr = &normalized

// After:
*col.DefaultExpr = normalizeDefaultExpr(*col.DefaultExpr)
```

**【预期收益】**
- 每个含默认值列减少 1 次堆分配
- 降低 GC 标记对象数量

### 问题 4：`canonicalizeTableInPlace` 重建 map 未按容量预分配

**【问题定位】**
- `internal/normalize/normalize.go:32`

**【缺陷分析】**
`make(map[string]*model.Column)` 未指定容量，列较多时触发多次 rehash。

**【优化方案】**
按 `len(table.Columns)` 预估容量。

**【代码对比】**
```go
// Before:
newColumnByName := make(map[string]*model.Column)

// After:
newColumnByName := make(map[string]*model.Column, len(table.Columns))
```

**【预期收益】**
- 减少 map 扩容和 rehash 次数
- 稳定化 normalize 延迟

## 二、工业级代码质量（Production-Ready Quality）

### 问题 5：解析错误返回丢失细节上下文，定位成本高

**【问题定位】**
- `internal/parser/parser.go:69-71` `ParseSQL`

**【缺陷分析】**
当前只返回 `parsing completed with %d errors`，未包含首个错误位置/语句片段，调用方很难快速定位。

**【优化方案】**
保留 `%w` 错误链，并附首个错误摘要。

**【代码对比】**
```go
// Before:
return p.schema, fmt.Errorf("parsing completed with %d errors", len(p.errors))

// After:
first := p.errors[0]
return p.schema, fmt.Errorf("parsing completed with %d errors, first: %w", len(p.errors), first)
```

**【预期收益】**
- 故障定位时间显著缩短
- 错误链可被上层 `errors.Is/As` 利用

### 问题 6：`loadEnumTypes` 的 `rows.Err()` 未补充上下文

**【问题定位】**
- `internal/introspect/enums.go:53-55`

**【缺陷分析】**
相比同目录其他函数，这里直接 `return err`，错误信息缺失 query 场景上下文。

**【优化方案】**
统一包装错误上下文。

**【代码对比】**
```go
// Before:
if err := rows.Err(); err != nil {
    return err
}

// After:
if err := rows.Err(); err != nil {
    return fmt.Errorf("iterate enum rows: %w", err)
}
```

**【预期收益】**
- 日志可读性提升
- 线上问题归因更直接

**【问题定位】**

## 三、Go 语言原生惯用法（Idiomatic Go / Effective Go）

### 问题 8：`renderCreateIndex` 未对列名做 identifier quoting

**【问题定位】**
- `internal/render/render.go:177-179` `renderCreateIndex`

**【缺陷分析】**
当前 `columns := strings.Join(idx.Columns, ", ")` 直接拼接列名，遇到保留字/大小写/特殊字符会生成非法 SQL，也有注入风险边界。

**【优化方案】**
逐列调用 `quoteIdentifier` 后再拼接。

**【代码对比】**
```go
// Before:
columns := strings.Join(idx.Columns, ", ")

// After:
quotedCols := make([]string, len(idx.Columns))
for i, c := range idx.Columns {
    quotedCols[i] = quoteIdentifier(c)
}
columns := strings.Join(quotedCols, ", ")
```

**【预期收益】**
- 消除非法 SQL 边界
- 提升跨 schema/命名风格兼容性

### 问题 9：`Parser.Errors()` 暴露内部切片，存在外部篡改风险

**【问题定位】**
- `internal/parser/parser.go:305-307`

**【缺陷分析】**
返回内部切片引用，上层可意外修改 parser 内部状态（非预期副作用）。

**【优化方案】**
返回防御性拷贝。

**【代码对比】**
```go
// Before:
func (p *Parser) Errors() []error { return p.errors }

// After:
func (p *Parser) Errors() []error {
    out := make([]error, len(p.errors))
    copy(out, p.errors)
    return out
}
```

**【预期收益】**
- 降低共享状态副作用
- API 行为更可预期

### 问题 10：有状态 `Differ`/`Parser` 对象在并发复用场景不安全

**【问题定位】**
- `internal/diff/differ.go:19-21, 37-41`
- `internal/parser/parser.go:35-39, 50-55`

**【缺陷分析】**
两者都在实例字段中缓存可变状态（`lastWarnings`、`errors/sql/schema`）。当前 CLI 串行使用没有问题，但如果未来作为库被并发复用会触发 data race。

**【优化方案】**
明确文档“非并发安全”，或改为无状态 API（每次调用创建局部 context）。

**【代码对比】**
```go
// Before:
type Differ struct { lastWarnings []string }

// After:
// 方案A：文档声明 not goroutine-safe
// 方案B：Diff 返回 warnings，不在对象内缓存状态
func Diff(source, target *model.Schema) (ops []Operation, warnings []string)
```

**【预期收益】**
- 消除未来并发化隐患
- 让 API 线程安全语义清晰

## 四、架构合理性与工程化（Architecture & Scalability）

### 问题 11：`cmd` 层仍承载 source-adapter 逻辑，边界耦合偏高

**【问题定位】**
- `cmd/migra/diff.go:57-99` (`loadSchemaWithContext`, `loadFromDB`, `loadFromSQLFile`)

**【缺陷分析】**
命令层既做参数入口，又做源适配（SQL 文件/DB）。当未来新增 source（HTTP、S3、git ref、stdin）时，`cmd` 将持续膨胀。

**【优化方案】**
抽出 `internal/source` 包，通过策略模式统一加载器；`cmd` 仅做 flag 解析与调用。

**【代码对比】**
```go
// Before: cmd 直接分支 source 类型
func loadSchemaWithContext(...) (*model.Schema, error) { ... }

// After: source registry + strategy
// internal/source/loader.go

type Loader interface {
    Match(source string) bool
    Load(ctx context.Context, source string, opt LoadOptions) (*model.Schema, []error, error)
}
```

**【预期收益】**
- 新增 source 类型改动面从“cmd+app+tests”收敛到 `internal/source`
- 降低命令层复杂度

---

### 问题 12：`plan.addDependencies` 以类型分支耦合具体 op，扩展成本高

**【问题定位】**
- `internal/plan/dag.go:77-119`

**【缺陷分析】**
每新增一种 Operation 都要修改 `switch`，违反开闭原则；复杂度已达 `gocyclo=13`。

**【优化方案】**
让 `diff.Operation` 暴露依赖声明（例如 `DependsOn() []model.ObjectKey`），`plan` 仅消费依赖数据，不关心具体 op 类型。

**【代码对比】**
```go
// Before:
switch op := node.Op.(type) {
case *diff.AddColumnOp:
    ...
}

// After:
type Operation interface {
    Kind() Kind
    ObjectKey() model.ObjectKey
    DependsOn() []model.ObjectKey
    IsDestructive() bool
}

for _, depKey := range node.Op.DependsOn() {
    if depNode := d.findNodeByOpKind(depKey, diff.KindAddTable); depNode != nil {
        d.AddDependency(node, depNode)
    }
}
```

**【预期收益】**
- `plan` 与 `diff` 解耦
- 新增操作类型无需频繁改动 DAG 核心
- 降低圈复杂度与回归风险
