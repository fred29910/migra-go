## 1. 概述

本文档描述了 migra-go 项目的全面改进计划，采用渐进式改进策略，分四个阶段实施。改进目标包括代码质量优化和文档完善，旨在提高项目的可维护性、可靠性和用户体验。

## 2. 当前状态分析

### 2.1 项目概况
- **项目**: migra-go - PostgreSQL Schema 差异比较工具
- **技术栈**: Go 1.26.2, Cobra, Viper, pgx v5, pg_query_go v6
- **架构**: 五阶段流水线（Source → Parser → Normalize → Diff → Plan → Render）
- **版本**: v0.2.1

### 2.2 现有问题
1. **编译错误**: `internal/diff/diff_columns_test.go` 中 `setOp.Default` 字段不存在
2. **已知 bug**: `docs/bugs/` 目录有 5 个未解决的问题
3. **测试覆盖率不均**: 
   - `internal/introspect`: 3.2%
   - `internal/parserutil`: 0%
   - `internal/model`: 34.6%
   - `internal/cmd/migra`: 29.4%
4. **文档需要更新**: 架构文档与代码实现可能存在偏差

## 3. 改进目标

## 4. 实施方案：渐进式改进

### 4.1 第一阶段：修复关键问题（1-2天）

#### 4.1.1 目标
确保项目基础稳固，消除阻塞问题。

#### 4.1.2 具体任务
1. **修复编译错误**
   - 文件: `internal/diff/diff_columns_test.go`
   - 问题: `setOp.Default` 字段不存在
   - 解决方案: 检查 `SetDefaultOp` 结构体定义，修复字段访问

2. **解决已知 bug**
   - 处理 `docs/bugs/` 中的 5 个问题:
     - `2026-05-15-github-release-403-permission-denied.md`
     - `2026-05-15-index-mutation-table-not-found.md`
     - `2026-05-15-json-format-output-mismatch.md`
     - `2026-05-15-multi-schema-diff-create-schema-stmt.md`
     - `2026-05-15-multi-schema-diff-duplicate-table.md`

3. **验证修复**
   - 运行 `make test` 确保所有测试通过
   - 运行 `make ci` 确保通过所有检查
   - 更新相关测试用例

#### 4.1.3 成功标准
- `make test` 通过所有测试
- `make ci` 通过所有检查
- 已知 bug 列表清零

#### 4.1.4 风险
- **低风险**: 修复现有问题，不引入新功能

#### 4.1.5 交付物
- 修复后的代码
- 更新的测试文件
- bug 解决文档

### 4.2 第二阶段：提高测试覆盖率（3-5天）

#### 4.2.1 目标
补充低覆盖率包的测试，提高整体代码质量。

   - 当前覆盖率: 0%
   - 目标覆盖率: > 30%
   - 重点: 类型映射、表达式解析、工具函数

3. **为 internal/model 添加测试**
   - 当前覆盖率: 34.6%
   - 目标覆盖率: > 60%
   - 重点: 数据模型操作、序列化/反序列化、边界条件

4. **为 internal/cmd/migra 添加更多集成测试**
   - 当前覆盖率: 29.4%
   - 目标覆盖率: > 40%
   - 重点: CLI 参数解析、配置加载、端到端流程

#### 4.2.3 成功标准
- 各包测试覆盖率达到目标
- 测试通过率 100%
- 无新增编译错误

#### 4.2.4 风险
- **中等风险**: 需要编写新测试，可能发现新的 bug

#### 4.2.5 交付物

### 4.3 第三阶段：代码质量优化（5-7天）

#### 4.3.1 目标
改进代码结构、错误处理和性能。

#### 4.3.2 具体任务
1. **改进错误处理**
   - 添加哨兵错误: `ErrNotFound`, `ErrInvalidConfig`, `ErrParseFailed`
   - 统一错误信息格式: 使用 `fmt.Errorf("context: %w", err)` 模式
   - 改进错误包装: 确保所有错误都有足够的上下文信息

2. **重构重复代码**
   - 提取公共函数:
     - identifier quoting (`quoteIdentifier`, `quoteQualifiedIdentifier`)
     - type normalization (`normalizeDataType`)
     - string comparison utilities
   - 消除代码重复: 合并相似的处理逻辑

3. **优化性能**
   - 分析内存使用热点
   - 优化关键路径:
     - diff 算法
     - SQL 解析
     - 数据库内省查询
   - 添加性能基准测试

4. **改进代码结构**
   - 调整包边界: 提高内聚性
   - 集中工具函数: 考虑创建 `internal/util` 包
   - 改进接口设计: 确保接口小而专注

#### 4.3.3 成功标准
- 错误处理一致性提高
- 代码重复率降低
- 性能基准测试显示改进
- 代码可读性提高

#### 4.3.4 风险
- **中高风险**: 重构可能引入新 bug，需要充分测试

#### 4.3.5 交付物
- 重构后的代码
- 性能基准测试报告
- 更新的错误处理模式

## 7. 风险管理

### 7.1 风险识别
1. **技术风险**: 重构可能引入新 bug
2. **时间风险**: 任务可能超出预计时间
3. **资源风险**: 需要持续的开发时间

### 7.2 风险缓解
1. **充分测试**: 每个阶段完成后运行完整测试套件
2. **增量改进**: 采用小步快跑的方式，每步都可验证
3. **优先级管理**: 优先处理高价值、低风险的任务

## 8. 质量保证
