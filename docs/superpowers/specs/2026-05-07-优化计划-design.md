## 第一部分：错误上下文改进

### 问题 5：解析错误细节增强

**位置：** `internal/parser/parser.go:69-71` 的 `ParseSQL` 方法

**改动：** 在返回错误时，使用 `%w` 包装首个错误详情，而非仅报告数量。

```go
first := p.errors[0]
return p.schema, fmt.Errorf("parsing completed with %d errors, first: %w", len(p.errors), first)
```

**影响：** 仅 `internal/parser` 包，不改变 API 签名，故障定位时间显著缩短。

### 问题 6：枚举加载错误上下文

**位置：** `internal/introspect/enums.go:53-55` 的 `loadEnumTypes` 函数

**改动：** 为 `rows.Err()` 添加场景上下文包装，与同目录其他函数保持一致。

```go
if err := rows.Err(); err != nil {
    return fmt.Errorf("iterate enum rows: %w", err)
}
```

**影响：** 仅 `internal/introspect` 包，日志可读性提升，线上问题归因更直接。

## 第二部分：接口命名规范

### 问题 7：接口重命名

**位置：**
- `internal/app/diff_service.go:27` 的 `Service` 接口
- `internal/diff/differ.go:9` 的 `Engine` 接口
- `internal/plan/plan.go:23` 的 `Engine` 接口

**改动：** 按职责重命名，提升跨包可维护性。

| 包 | 原名 | 新名 |
|---|---|---|
| internal/app | Service | DiffService |
| internal/diff | Engine | DiffEngine |
| internal/plan | Engine | Engine |

**实施：** 使用 Go 重命名工具逐个重命名，更新所有引用点，运行 `go build ./...` 和 `go test ./...` 验证。

**影响：** 纯重构，不改变方法签名，降低认知负担。

## 第三部分：架构解耦

### 问题 11：Source Loader 解耦

**位置：** `cmd/migra/diff.go:57-99` 的 `loadSchemaWithContext`、`loadFromDB`、`loadFromSQLFile`

**问题：** 命令层既做参数入口，又做源适配，新增 source 类型时 `cmd` 会膨胀。

**方案：** 创建 `internal/source` 包，抽出加载逻辑。

```go
type Loader interface {
    Match(source string) bool
    Load(ctx context.Context, source string, opt LoadOptions) (*model.Schema, []error, error)
}

type Registry struct { loaders []Loader }
func (r *Registry) Load(ctx context.Context, source string, opt LoadOptions) (*model.Schema, []error, error)
```

**实施步骤：**
1. 创建 `internal/source` 包，定义 `Loader` 接口和 `Registry`
2. 实现 `DBLoader` 和 `SQLFileLoader`
3. 修改 `cmd/migra/diff.go` 使用 `source.Registry`
4. 可选：调整 `internal/app` 的 `DiffService` 接收 `Loader`

**预期收益：** 新增 source 类型改动面收敛到 `internal/source`，降低命令层复杂度。

### 问题 12：Operation 依赖声明

**位置：** `internal/plan/dag.go:77-119` 的 `addDependencies`

**问题：** 每新增一种 Operation 都要修改 switch，违反开闭原则，圈复杂度 13。

**方案：** 让 Operation 自声明依赖，`plan` 仅消费依赖数据。

```go
type Operation interface {
    Kind() Kind
    ObjectKey() model.ObjectKey
    DependsOn() []model.ObjectKey
    IsDestructive() bool
}
```

**实施步骤：**
1. 为 `diff.Operation` 添加 `DependsOn()` 方法（或创建新接口）
2. 所有 Operation 实现返回其依赖的 ObjectKey 列表
3. 修改 `plan.addDependencies`，遍历 `op.DependsOn()` 而非 switch 分支
4. 删除或简化原有 switch 逻辑

**预期收益：** `plan` 与 `diff` 解耦，新增操作类型无需改 DAG 核心，圈复杂度降低。

## 实施优先级

本计划包含 5 个问题，按以下顺序实施：

1. **错误上下文改进**（问题 5、6）— 独立改动，风险低
2. **接口命名规范**（问题 7）— 纯重构，可借助工具批量重命名
3. **架构解耦**（问题 11、12）— 可独立实施，建议先 11 后 12

1. `go build ./...` 编译通过
2. `go test ./...` 全量测试通过
3. `go vet ./...` 无警告
4. 问题 5、6：错误信息包含场景上下文，可用 `errors.Is/As` 判断

6. 问题 11：`cmd` 层不再包含 source-adapter 逻辑
7. 问题 12：`plan.addDependencies` 无 switch 分支，圈复杂度降低
